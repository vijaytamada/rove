# Testing

## How to run everything
Prerequisites: Docker infra running (`docs/DEV_SETUP.md`), backend and website running for the QA scripts.

| What | Command | Needs |
|---|---|---|
| Backend unit tests | `cd backend && npm test` | nothing |
| Backend end-to-end tests | `cd backend && npm run test:e2e` | Postgres + Redis (`docker compose up -d`) |
| Backend lint / build | `npm run lint` · `npm run build` | |
| Website lint / build | `cd frontend && npm run lint && npm run build` | |
| Flutter | `cd flutter && flutter analyze && flutter test` | |
| API security sweep | `node tools/qa/sweep.mjs` | backend running + seeded |
| Concurrency probes | `node tools/qa/race.mjs` | backend running + seeded (cleans up after itself) |
| Website page-by-role matrix | `node tools/qa/pages.mjs` | backend + website running + seeded |
| Backup restore check | `tools/ops/backup-db.sh` then `tools/ops/verify-backup.sh <file>` | Docker infra running (restores into a scratch database and compares row counts) |

Notes
- e2e tests create data prefixed `e2e-`/`E2E-` and delete it afterwards; seed data is never touched. Don't name manual test data with those prefixes (the cleanup would delete it).
- `sweep.mjs` deliberately fails many logins, which locks a staff account for 15 minutes. Clear it with `docker exec rove-redis sh -c "redis-cli --scan --pattern 'login:fail:*' | xargs -r redis-cli del"`.
- The QA scripts read seed credentials from the root `.env`.
- Stop the dev backend (or run it with `TELEMETRY_PROVIDER=mock`) before `npm run test:e2e`: with the simulator on, it also writes readings for the tests' scooters in the shared database. The e2e tests give every request its own made-up client address so the per-IP limits do not add up across tests; `sweep.mjs` and `pages.mjs` clear the failed-login and request counters (`login:fail:*`, `login:ip:*`, `rl:*`) when they start, because in development every client shares one address.

## Known limitations and accepted risks
- Telemetry: only the simulator and `POST /telemetry` exist; one shared device key (no per-device credentials yet); no check of the staff odometer against telemetry; the live map polls (no push) and loads every visible scooter (fine for hundreds, not thousands); OpenStreetMap's public tiles are for light use, so production needs a tile provider; the simulator's battery and odometer come from the scooter's last staff reading, not from real hardware.
- Identity: only the mock provider exists; the vendor's hosted-check link, its real webhook format and the Aadhaar legal review are open. The support reset has no screen, only the API. A pending check with no answer can be restarted after 15 minutes, which uses a try.
- Audit trail: it records successful staff writes only (not who read what, and not failed attempts); it has no IP address (behind the website's server every request would carry the same one); no retention or export yet.

- Payment and identity checks are mocks (Phases 9-10).
- The app shows city time exactly only for India (fixed offset); for another time zone it falls back to the device clock until a second zone exists.
- Holds are expired by the minute job (and still lazily when a booking, list or new booking touches them), so an expired hold is marked within about a minute of running out. If the backend is not running, nothing expires or reminds until it is back; reminders are skipped only if their window passed while it was down (a pickup reminder after the start is never sent).
- `npm audit` still reports 4 high advisories in the **`prisma` command-line tool** (dev dependency; its bundled MySQL driver and a config helper); not part of the running API, we use PostgreSQL, and no patched stable Prisma exists yet (7.10 is the latest; 8.0 is a release candidate). Revisit when one is released.
- Per-IP limits (login failures, quote, browsing, one-time codes) depend on the right client address: the website forwards the visitor's address from the proxy in front of it, which must overwrite `X-Forwarded-For`, and the API needs `TRUST_PROXY`. Without that, everyone behind one address shares a counter (and, in development, everyone on the machine does).
- A locked email can be locked by anyone who keeps guessing (a standard trade-off); the lock lasts 15 minutes.
- Swagger UI (`/api/docs`) is off in production unless `SWAGGER_ENABLED=true`. The website's Content-Security-Policy allows inline styles.
- Not tested: iOS, physical Android devices, browsers other than Chromium, screen readers (basic labels/contrast follow the design rules), load/performance at scale, real SMS/payment/KYC providers (mocks until Phases 9-10).
- On a no-show the customer's price card still says "Returned after you bring the scooter back" under the deposit (cosmetic; the refund line below it is correct).
- `pages.mjs` expects the seeded scooter `BLR-001` to be at its station: finish or return any ride you started by hand before running it.
- Dashboards: utilization shows 0% in the dev data because test rides last seconds; it is meaningful with real rides. Money figures include held deposits (labelled), so they are not earnings. A scooter out on a ride is counted from the ride, not from a station. Large networks would want these queries cached or pre-aggregated (Phase 12).
- Notifications: delivery outside the app is a log line (mock) until SMS in Phase 9 (India DLT registration needed); only customers get messages (staff are not told of failed refunds or overdue rides yet); there is no per-message preference or opt-out; an optional customer email and the email channel were left out (see the Decision Log). The inbox shows the latest 50.
- Settlement: charges and refunds are mock-money (Phases 9-10). A charge cannot yet be waived or changed after staff enter it, so a wrong damage fee is only fixable by collecting more. Gateway refund confirmations (Razorpay `refund.processed`, Cashfree refund webhooks) arrive in Phase 10; until then "refund sent" means the provider call returned success.
